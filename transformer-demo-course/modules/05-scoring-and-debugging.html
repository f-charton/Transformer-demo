Scoring, saving and debugging

How an answer is graded, what the real numbers say, how a run survives a crash, and what to check when training misbehaves.

Marking with partial credit

A good maths teacher does not only write "wrong". They note whether the size of the answer was right and only the sign slipped. This project grades the same way.

At evaluation time the model writes its answer alone, token by token, until it produces <eos>. The tokens are turned back into an integer and passed to this function.

CODE · src/envs/generators/amplitudes.py 
    def evaluate(self, problem, question, answer, hyp, metrics):        if hyp is None:            return {"is_valid": -1}        if hyp == answer:            return {"is_valid": 1, "correct_sign":1, "correct_module": 1}        same_sign = (hyp * answer > 0)        same_module = (abs(hyp) == abs(answer))        res = {"is_valid": 0}        res["correct_sign"]= 1 if same_sign else 0        res["correct_module"]= 1 if same_module else 0        return res
PLAIN ENGLISH

Grade one prediction (hyp, short for hypothesis) against the true answer.

If the model's tokens could not be read as a number at all, mark it malformed (-1).

If it matches exactly, full marks on everything.

Otherwise: do the two numbers have the same sign? (Their product is positive only if they do.)

Do they have the same size once the sign is ignored?

Record it as wrong overall...

...but note separately whether the sign was right...

...and whether the size was right.

Hand the marks back.

So the model nearly always gets the size of the coefficient. Most of its mistakes are a wrong sign on an otherwise correct number. The single accuracy number hides that; the partial-credit marks reveal it.

One number is never the whole story

Overall accuracy sat near 70% in all four epochs, yet underneath the model was flipping between favouring plus and favouring minus. Whenever a score looks stable, ask for it to be broken down by category. This habit catches more problems than any other.

Save points

After every epoch the Trainer writes a checkpoint. When a run starts, the first thing the Trainer does is look for one.

CODE · src/trainer.py 
        auto_path = os.path.join(self.params.dump_path, "checkpoint.pth")        if os.path.isfile(auto_path):            checkpoint_path = auto_path        elif self.params.reload_checkpoint != "":            checkpoint_path = self.params.reload_checkpoint            assert os.path.isfile(checkpoint_path)        else:            return
PLAIN ENGLISH

Work out where this run's own checkpoint would be.

If one is already there, the run was interrupted earlier. Use it.

Otherwise, if you named a checkpoint with --reload_checkpoint, use that one...

...and stop with an error if the file does not exist.

Otherwise there is nothing to reload. Start from scratch.

💾
checkpoint.pth

Rewritten at the end of every epoch. The "continue from here" file.

🏆
best-<metric>.pth

Written only when a score you listed in --validation_metrics beats its previous best.

🚨
checkpoint_nan.pth

Written if the loss stops being a number. The run then exits so you can inspect what happened.

When training misbehaves

Four symptoms cover most bad runs. The first two come with the author's own notes from the notebook.

📉

Training loss falls, test loss rises

The model is memorising. This is overfitting. The notebook sees it with 5,000 examples and almost none with 20,000.

🪨

Loss never comes down

Suspect the learning rate first. The notebook notes that 0.01 does not learn and 0.001 does.

🛑

Stops at once with AssertionError

A sanity check failed before training: a missing file, a width that does not divide by the heads, or a task name that does not match.

🔁

A "new" run resumes an old one

The experiment folder already held a checkpoint.pth, so the Trainer reloaded it. Use a fresh --exp_id.

⚠️
Two easy mistakes with the data flags

The files in data/ ship zipped and the loader reads plain text, so they must be unzipped first (the notebook's first cell does this). And reload_data needs the task name in front: amplitude:../data/5.train, not just the path.

What you can now say out loud

You have the vocabulary to direct changes to this code precisely.

1
"Add a flag for..."

Every setting is a flag defined in train.py's parser.

2
"Change the tokenizer so that..."

How text becomes tokens lives in src/envs/tokenizers/, and it sets the vocabulary size.

3
"Report this metric broken down by..."

Marks come from the generator's evaluate; the Evaluator averages and logs them.

4
"Is this overfitting, or is the learning rate wrong?"

Compare training loss with validation loss in train.log before changing anything.
